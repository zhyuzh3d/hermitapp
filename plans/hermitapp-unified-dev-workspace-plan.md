# HermitApp 智能体开发服务重构计划

版本 3.0，2026-09-21。本文件是 HermitApp 智能体开发服务的唯一实施计划。本轮只重构服务模型、工具合同和开发端协作方式，不执行代码修改、构建、设备安装或线上发布。

## 一、目标和技术判断

目标是让智能体在新对话中可以恢复一个设备级开发连接，随后按 `happId` 操作任意已安装 happ，并用最少的调用完成准备、开发、热更新、阶段性安装和正式安装。服务应该把可用能力、当前状态和推荐做法说清楚，但不把智能体限制在一个 happ 或一条不可变流程上。

现有实现已经具备认证 MCP、开发工作区、revision、原子提交、上传和刷新等基础能力，主要问题是入口仍容易被理解成“绑定一个 happ 的会话”，工具目录偏工具清单，智能体需要自行串联多个调用，设备端没有清晰的开发版下载和整体覆盖语义，热更新后的刷新和状态恢复也没有收敛成一个原子意图。

本计划的明确判断如下：

- 会话是设备级、全局的；happ 是每次操作的目标，不是会话的所有权。
- 设备端不做开发端与设备端的三方合并、逐文件冲突裁决或版本优先级猜测。服务只提供设备状态和可选整树下载，覆盖方向由智能体根据本地版本读取结果询问用户后明确指定。
- 热更新必须有一站式原子接口；单文件、上传和刷新等低层接口继续保留，以支持特殊场景和故障排查。
- 工具目录升级为意图路由和按需说明。最佳实践是推荐文本，不是服务端强制状态机。
- 密码继续采用现有六位密码模型，只把手工密码字符集扩展为六位数字或大小写字母；不引入 TLS、配对、per-client token 或其他额外认证层。

## 二、统一领域模型

### 2.1 全局连接和目标

连接 profile 表示一个开发服务地址和传输方式：HTTP(S) 地址或 ADB forwarding 标识、服务端能力摘要、最近一次成功连接时间和凭据引用。`open_agent_session` 成功后返回设备级 `sessionId`，session 不保存唯一 happ，也不因切换目标而重新认证。

所有会改变或读取 happ 的操作都携带目标：

```json
{
  "happId": "com.example.notes",
  "appId": "optional-instance-id"
}
```

`happId` 是发布包声明的稳定身份；同一 `happId` 存在多个本机实例时必须显式指定 `appId`，只有一个实例时服务可以解析。服务不得把第一次选择的 happ 固化成 session 的权限边界。连接成功后，智能体可以先列出已安装 happ，再在任意目标之间切换。

`source` 与 `runtimeMode` 保持正交：开发工作区是一个 happ 的可变 DEV 树，正式 release 是不可变版本；`runtimeMode=dev` 表示启动 DEV 树，`runtimeMode=stable` 表示启动 active stable release。切换目标、版本或运行方式都不能隐式改变 `happId`、实例、数据或授权。

### 2.2 开发状态和版本语义

设备对每个 happ 返回以下小型状态，不默认传输完整文件树：

- `devVersion`：开发工作区声明的版本，可用于提示和发布决策；
- `devRevision`：设备端开发树的单调修订号，用于恢复、日志和可选写入保护；
- `treeHash`、文件数量和总大小：用于确认状态是否变化，不用于推断哪一侧优先；
- 当前 `runtimeMode`、active stable release、页面可见性和最近渲染结果。

版本号不是内容一致性的证明。智能体必须读取本地项目版本，向用户呈现“设备开发版 vs 本地开发版”，由用户决定以设备为准、以开发端为准，还是先下载设备开发树后自行比较。服务不自动比较、不自动合并、不以版本号替用户做覆盖决定。

## 三、连接恢复和意图路由

### 3.1 新对话的恢复顺序

开发端 helper 按以下顺序工作：

1. 读取本机保存的连接 profile，先尝试地址和凭据引用对应的服务；
2. 通过 discovery 获取服务版本、认证方式、`runId`、意图目录摘要和 `schemaDigest`；
3. 使用六位密码建立或恢复全局 session；
4. 认证失败、地址失效或密码被修改时，停止盲目重试并向用户询问最新地址或密码；
5. 连接恢复后只刷新轻量状态，不重复拉取未变化的指南、schema 或所有文件。

地址和密码可以由用户明确要求后保存到开发端的本地凭据存储；不得写入项目文件、Skill、提交记录、普通日志或模型上下文。服务端不会因为 session 长连接而改变逐请求密码验证语义。

### 3.2 意图目录而非工具清单

认证前 discovery 只返回连接方法和能力摘要。认证后返回按意图分组的目录，每项只有名称、适用情况、前置条件、主要副作用和 `schemaRef`，例如：

| 意图 | 推荐能力 | 说明 |
| --- | --- | --- |
| 连接和恢复 | `open_agent_session`、`resume_agent_session` | 建立设备级 session，可操作任意已安装 happ |
| 目标选择和状态 | `list_installed_happs`、`get_happ_dev_status` | 读取目标、开发版本、revision 和运行方式 |
| 准备开发 | `prepare_happ_development` | 恢复或重新初始化指定 happ 的 DEV 工作区，可选同时进入 DEV |
| 日常开发 | `hot_update_happ` | 原子提交变化、刷新页面并恢复页面状态 |
| 页面控制 | `get_page_state`、`refresh_happ_page` | 获取当前页面或按 path/query/hash 刷新 |
| 设备代码 | `download_dev_tree` | 按用户决定下载设备端整棵开发树 |
| 阶段性版本 | `promote_dev_release` | 将 DEV 树安装成稳定 release，但继续以 DEV 方式运行 |
| 正式交付 | `install_happ_release`、`switch_happ_runtime_mode` | 安装 ZIP 并明确切换回 stable |
| 诊断和低层操作 | `get_dev_diagnostics` 及单文件接口 | 特殊文件、故障排查和人工编排 |

目录只提供语义路由，不要求智能体严格遵循表中顺序。智能体需要某个意图的完整参数时，再按 `schemaRef` 读取对应 schema 和短说明，并按 `schemaDigest` 缓存；标准 `tools/list` 只在明确需要底层工具时读取。指南、Bridge 合同和二进制说明同样按需加载，彼此独立失效。

服务端只强制真正的安全和一致性前置条件，例如目标存在、路径合法、写入原子性和受保护目标拒绝；不把推荐流程实现成不可绕过的状态机。

## 四、推荐开发生命周期

推荐主路径是：

`恢复或重新初始化准备 → 进入 DEV 运行 → 开发与原子热更新 → 阶段性 DEV 安装并继续开发 → 最终打包正式安装 → 明确切回 stable`。

它是智能体的默认建议，不是调用顺序的硬约束。每一步都可单独调用，失败时返回已经完成的阶段和可继续使用的目标状态。

### 4.1 恢复或重新初始化

`prepare_happ_development` 是幂等的高层入口，至少支持：

- `strategy=resume`：复用指定 happ 的现有 DEV 树，返回设备开发版本和 revision；
- `strategy=reset`：显式放弃现有 DEV 树，并从用户指定的来源重新建立；来源可以是 active stable release 或本次上传的开发树；
- `startRuntimeMode=dev|unchanged`：需要时在同一请求结束时进入 DEV，特殊情况仍可单独调用 `enter_happ_dev_mode`。

`reset` 是明确的破坏性操作，服务必须返回将被替换的 `devRevision` 并要求调用方明确给出来源。恢复不应自动下载整个文件树，也不应因为本地版本不同而自行覆盖。

### 4.2 设备端和开发端的整体选择

准备完成后，智能体读取本地版本和必要的本地摘要，向用户提出一个简单选择：

- 设备为准：使用 `download_dev_tree` 拉取整树，开发端以下载结果为工作副本；
- 开发端为准：使用 `replace_dev_tree` 或对应的高层参数，以本地整树原子覆盖设备 DEV 树；
- 先下载再决定：只下载，不要求服务端做差异分析。

服务只接受显式的整体覆盖请求。`devRevision` 默认用于诊断；需要防止过期写入时调用方可以携带 `guardRevision`，也可以显式 `force=true` 覆盖。服务不得暗中把过期 revision 变成复杂冲突流程。文件清单摘要可以返回，但不默认生成逐文件 diff、三方合并或“版本优先”结论。

`download_dev_tree` 返回 ZIP 或受控目录下载句柄，下载内容仍遵守路径、大小、数量和摘要校验。下载句柄和上传句柄都属于服务临时对象，不能让设备任意访问外部地址。

### 4.3 进入 DEV 和切换运行方式

`enter_happ_dev_mode`、`switch_happ_runtime_mode` 都按目标 `happId` 工作。进入 DEV 只改变该目标的启动通道，不改变来源、数据、授权或其他 happ。切换 stable 也必须明确指定目标；服务不因正式安装完成而偷偷切换运行方式。

## 五、原子热更新和页面刷新

### 5.1 一站式热更新

`hot_update_happ` 是日常开发的默认接口，一次调用完成：接收变更或上传句柄、在 staging 中校验、原子提交 DEV revision、按策略刷新当前页面、尝试保存和恢复开发页面状态，并返回可诊断结果。

变更源统一表示为以下三类之一：

- 小文本或小二进制的 `inline` 数据；
- 由服务返回临时上传地址后得到的 `uploadHandle`，适合大文件；
- 服务签发的受控 `sourceUrl`，表示已经上传到开发服务的对象地址。

不支持让设备按任意外部 URL 抓取文件；这样既无法保证开发结果可重复，也会把服务变成不必要的网络代理。单文件地址能力只针对服务签发的对象地址。

高层接口可同时处理多个新增、覆盖、删除和移动操作；设备在全部内容、路径、大小和摘要通过校验后一次替换 DEV 指针。默认 `refreshMode=auto`：

- 只有 CSS 变化时，复用当前文档并等待新 stylesheet 加载和下一帧绘制；
- HTML、JavaScript、路由或未知资源变化时，在同一 WebView reload 当前页面；
- 当前页面不可见时只提交并返回 `not-visible`，不擅自切换前台。

刷新前由设备尝试读取 `hermitDevState`（当前 path、query、hash、滚动位置及应用声明的可序列化状态），刷新后在 DOMContentLoaded 和绘制确认后恢复。默认是 best-effort 并报告 `stateSaved`、`stateRestored` 和失败原因；需要严格保证时调用方可以使用 `statePolicy=require`。提交、刷新和渲染回执必须分开返回，不能以“写入成功”冒充“页面已经可见”。

### 5.2 保留的低层能力

特殊情况仍可单独调用 `apply_dev_files`、`put_dev_file`、`replace_dev_tree`、`refresh_happ_page`、`get_page_state` 和 `wait_dev_render`。这些接口与高层接口使用同一 staging、摘要校验和 revision 机制，不形成第二套写入协议。智能体只有在高层接口无法表达需求或需要诊断时才使用它们。

## 六、阶段性版本和正式安装

### 6.1 DEV 阶段性安装

`promote_dev_release` 将当前 DEV 树按显式版本号生成不可变 stable release，并完成安装校验；安装后目标仍保持 `runtimeMode=dev`，同时以安装结果重新确认 DEV 工作区的基线并返回新的 `devRevision`。这样可以在阶段性版本升级后继续热更新，不把每次保存都变成正式安装。

版本只能由调用方显式指定或显式请求 bump。热更新不自动递增版本，服务也不把设备 revision 当作发布版本。`promote_dev_release` 保留同一 `happId`、实例、数据和 grants，稳定 release 仍不可变。

### 6.2 最终 ZIP 正式安装

`install_happ_release` 接收开发端提供的 ZIP 数据或服务签发的上传句柄，执行一次完整安装事务：校验包身份、版本、路径、大小和摘要，生成新 stable release，并原子更新 active release。它不默认修改 `runtimeMode`；完成后由智能体在用户确认下调用 `switch_happ_runtime_mode({runtimeMode:"stable"})`。

正式安装与仓库线上发布严格分离。设备安装不能隐式发布 URL、修改服务器或操作 HermitUI；失败时只报告安装阶段，不要求智能体重新上传或重新构建已经确认有效的包。

## 七、密码和服务端会话

密码规则只做兼容扩展：默认生成六位数字；用户手工设置时允许恰好六位 ASCII 数字、大小写字母组合（字符集 `[0-9A-Za-z]`）。旧六位数字密码继续有效，修改密码后旧密码立即失效。错误验证达到五次后按现有策略对来源 IP 锁定并拒绝后续请求；成功请求不重置其他 IP 的失败计数。

不增加 TLS、设备配对、per-client token、复杂密钥轮换或额外登录层。HTTP/ADB 只决定连接传输方式，不能改变同一套密码验证和 session 语义。长连接只用于降低重复建连成本，不能成为绕过认证的旁路。

## 八、实施分期

### 阶段 A：合同和目录收口

定义全局 session、目标 `happId/appId`、开发状态返回值、意图目录格式、按需 schema 引用和统一错误码。保留现有底层工具作为实现能力，先让 helper 能用一个 session 操作多个已安装 happ。

### 阶段 B：连接恢复和准备流程

实现 profile 恢复、discovery 摘要缓存、`prepare_happ_development` 的 resume/reset、设备开发版本读取和 `download_dev_tree`。删除单 happ session 的隐含假设；不实现服务端 diff 或自动合并。

### 阶段 C：原子热更新

实现 `hot_update_happ` 的统一输入、临时上传句柄、整批 staging、原子 revision、CSS/HTML/JS 刷新、`hermitDevState` 保存恢复和分段回执。同步保留单文件、单独刷新和整树接口。

### 阶段 D：稳定闭环

收敛 `promote_dev_release`、`install_happ_release` 和 `switch_happ_runtime_mode` 的版本与安装语义，验证 appId、数据、授权和运行通道都按目标保留或改变。更新 Skill，只写推荐做法，不写不可绕过的流程状态机。

### 阶段 E：定向验证

先运行 helper 合同测试和直接相关的 Kotlin 测试，再在真实设备验证：新对话恢复、同一 session 切换多个 happ、resume/reset、设备树下载、整体覆盖、单文件和多文件热更新、删除/移动、自动刷新与状态恢复、断线重连、阶段性 DEV 安装、ZIP 正式安装和切回 stable。除非用户另行要求，不构建 APK、不安装设备、不发布线上资源。

## 九、验收标准

1. 一个全局 session 建立后，可以在不重新认证的情况下读取和操作任意已安装 happ；没有默认绑定的单一 happ。
2. 新对话优先恢复已保存 profile；地址或密码失效时能给出明确错误并请求用户输入，不循环扫描或盲试。
3. discovery 首先返回意图摘要；schema、指南和底层工具描述按需读取并可按摘要缓存。
4. 准备接口返回设备 `devVersion/devRevision/treeHash`，智能体能读取本地版本并让用户选择整体方向；服务端不自动 diff、合并或猜测优先级。
5. 设备开发树可以按需整树下载；开发端整树覆盖是显式、可追踪、原子的，支持可选 revision guard 和明确 force。
6. 一次 `hot_update_happ` 能完成文件接收、原子提交、自动刷新、状态恢复和分段回执；失败不会暴露半棵 DEV 树。
7. CSS 更新不重载文档，HTML/JS 更新在同一 WebView 刷新并尽可能恢复当前页面状态；不可见页面不会被偷偷切到前台。
8. 阶段性 DEV 安装后仍保持 DEV 运行并可继续热更新；最终 ZIP 安装和切回 stable 是明确可审计的两个动作。
9. `happId`、实例、数据和 grants 在开发模式切换、阶段性安装和正式安装中只按合同变化，不因 session 或版本变化被隐式替换。
10. 密码默认六位数字，手工可用六位数字或大小写字母；五次失败 IP 锁定行为保持不变，没有引入额外认证体系。

## 十、明确不做

不做单 happ 会话、不做服务端三方合并和逐文件冲突裁决、不做版本号优先覆盖、不做每次保存构建稳定 ZIP、不把设备开发树直接当 stable release、不把推荐流程硬编码成状态机、不让设备抓取任意外部 URL、不引入第二套安装协议或额外密码加固，也不把设备正式安装和仓库线上发布合并成一个命令。

完成本计划后，智能体的默认行为应当很简单：恢复一次设备级连接，选择目标 happ，先读设备和本地版本让用户决定方向，准备 DEV，之后优先使用原子热更新；只有阶段性确认或最终交付时才安装版本，并由用户明确决定何时切回 stable。
