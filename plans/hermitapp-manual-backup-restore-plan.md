# HermitApp 手工备份与恢复实施计划

日期：2026-09-20。状态：待实施。

本计划只建设用户主动触发的备份与恢复，不引入自动备份、云同步、账号体系或公共目录中的运行数据库。目标是在正常覆盖升级中无损保留现有数据，并在用户卸载、换机或设备重置前已导出备份的前提下，恢复 HermitApp 设置和 happ 数据。

## 一、最终产品决策

HermitApp 的数据库、happ 代码和文件对象继续保存在应用私有目录。公共目录只保存完成校验的备份文件，不能作为运行数据库或对象存储目录。原因是 Android 分区存储、SAF 授权、SQLite WAL/锁、用户误改和数据泄露都使公共目录不适合作为在线运行存储。

Android 系统自动备份和设备迁移备份继续关闭。用户卸载 HermitApp 时，Android 必然删除应用私有数据，HermitApp 无法阻止；只有卸载前保存到用户选定外部位置的备份文件能够继续存在。卸载也会撤销原有 SAF 持久授权，因此重装后恢复时必须允许用户重新选择备份文件或目录，不能承诺自动重新获得旧目录权限。

设置的“系统”区域提供唯一备份入口，并固定提供三种操作：

1. **备份全部**：导出 Hermit 可迁移设置、所有 ready/archived happ 的现有单 happ 备份，以及可迁移的通知计划。
2. **备份 Hermit**：只导出 Hermit 自身非敏感、可迁移的用户设置，不包含任何 happ。
3. **备份单个 happ**：列出所有已安装 happ，每项提供独立备份按钮，复用现有 happ 备份语义。

同一区域提供“从备份恢复”。恢复入口先读取包内清单，自动识别 `full`、`settings` 或 `happ`，再进入对应流程；文件名只用于展示，不能决定备份类型或可信度。

## 二、现状与必须修复的问题

现有 `BackupCoordinator` 已能导出单个 happ 的配置、Hermit 记录、逻辑文件、当前 `activeReleaseId` 对应的本地代码和自定义图标，并能恢复为新实例或只替换已有实例的数据。现有 schema 3 备份继续作为合法的旧版单 happ 备份读取，不要求用户重新导出已有文件。

现有单 happ 备份只包含一个正式 release；其他历史 release 和开发工作副本不进入备份。全量备份必须复用这一合同，不额外引入版本历史、分支或开发目录。纯线上 happ 依靠 `liveUrl` 恢复；同时存在本地 release 和线上运行能力的 happ 仍保留当前活动正式 release 与 `runtimeMode`，恢复后继续使用备份声明的运行方式。

当前 `AppRegistry.onUpgrade()` 对旧 schema 采用删表重建，这是覆盖升级丢失 happ 的直接风险，必须在本功能之前修复。正式发布后的数据库升级只能使用逐版本、非破坏性 migration；任何未知 schema 必须停止启动并进入原生恢复页，不能清空数据库后继续运行。

覆盖安装只有同时满足以下条件才承诺保留数据：

- 包名保持 `io.github.zhyuzh3d.hermit`；
- 使用同一正式签名密钥；
- `versionCode` 单调增加；
- 通过系统更新或覆盖安装，不先卸载旧版本；
- Registry、通知数据库和其他持久数据均有已测试的非破坏性迁移。

## 三、备份范围

### 3.1 单 happ 备份

保持现有逻辑导出方式，不复制正在使用的 SQLite 文件：

- happ 展示名称、来源、运行方式、`happId`、`liveUrl`、`updateUrl`、`downloadUrl` 和允许跨 Origin 网络设置；
- 当前数据 generation 中的 Hermit 记录，以受限 JSONL 导出；
- FileStore 元数据和全部文件对象，保留 `logicalFileId`；
- 当前活动正式 release 的完整代码树；
- 自定义图标；
- 条目大小、SHA-256 和总量统计。

明确排除历史 release、开发工作副本、WebView Cookie/WebStorage/IndexedDB、登录态、Android 系统权限、Hermit grants、开发密码/token、临时句柄和操作日志。

### 3.2 Hermit 设置备份

只使用显式白名单导出稳定用户设置，不直接复制 SharedPreferences、Registry 数据库或 WebView Profile。首版白名单包括：

- 主题及界面偏好；
- 用户明确配置的语音/TTS 偏好；
- 其他经逐项确认不含设备身份、凭据和临时状态的全局设置。

开发服务开关与密码、局域网地址、系统权限观察值、诊断记录、官方 Shell 临时运行状态和所有系统生成标识不得恢复。新增设置只有在备份 schema 明确登记并有恢复测试后才能进入白名单。

### 3.3 全部备份

全部备份是一个带总清单的容器，内部包含：

- 一份 Hermit 设置备份；
- 每个 ready happ 的独立逻辑备份；
- 每个 archived 实例仍保留的数据备份及 archived 状态；
- 尚未触发或仍有效的本地通知计划。

通知只备份用户定义的计划内容、时间锚点和重复规则。已经投递的去重记录、在线通知 endpoint、Cookie 凭据、同步 cursor/ETag 不迁移；恢复后由用户重新授权通知并由 Scheduler 重新计算下一次触发时间。

“全部”仍不是 Android 应用沙盒的字节镜像。它不包含 WebView 登录态、系统权限和不可迁移的设备状态，恢复预览和结果页必须明确显示这些排除项。

## 四、文件格式与命名

新增统一外层清单 `hermit-backup.json`，首版 schema 为 `1`，至少包含：

```json
{
  "schema": 1,
  "backupType": "full",
  "createdAt": 1789891845000,
  "hermitVersionCode": 59,
  "hermitVersionName": "1.10.25",
  "happCount": 4,
  "entries": {}
}
```

`backupType` 只接受 `full`、`settings`、`happ`。所有非清单条目都必须在 `entries` 中登记大小和 SHA-256；路径执行大小、数量、大小写重复和穿越校验。全量包内部的每个 happ 保持独立边界，建议存为 `happs/<ordinal>/backup.zip`，由同一逻辑 exporter 写入，不允许通过临时公开文件拼接。

现有 schema 3 `backup.json` 没有外层类型时，恢复器只把它识别为旧版 `happ` 备份。未知新 schema 必须拒绝并提示升级 HermitApp，不能猜测字段或部分恢复。

系统文档创建器预填文件名，用户仍可修改保存位置和名称：

```text
Hermit-full-20260920-153045.hermit-backup.zip
Hermit-settings-20260920-153045.hermit-backup.zip
VibeDraw-20260920-153045.hermit-backup.zip
```

时间使用设备当前本地时间，格式固定 `yyyyMMdd-HHmmss`；happ 名称先移除路径字符和控制字符，再限制长度。文件名冲突交由系统文档提供者处理，业务层不得覆盖已有备份。

首版备份不加密。导出确认页必须提示文件可能包含笔记、附件和代码，应保存到可信位置；加密备份属于后续独立协议，不能在 ZIP 上临时附加自制弱加密。

## 五、导出流程

所有导出都由系统 `ACTION_CREATE_DOCUMENT` 选择目标，使用流式写入，不能先在内存生成完整 ZIP。流程固定为：

1. 读取目标集合和预计大小，检查 1 GiB/50,000 条目上限及可用空间；超限时在开始写入前失败。
2. 停止会修改目标数据的开发服务，给目标 happ 加备份只读锁，等待当前 Bridge 写事务结束。
3. 锁定实例、数据 generation 和 release lease，逐项导出逻辑记录、文件对象和代码。
4. 每个条目边写边计算大小与 SHA-256，最后写清单。
5. 关闭并刷出输出流后返回成功；取消、异常或空间不足返回失败，不能更新“最近备份”状态。
6. 释放锁和 lease，恢复此前允许恢复的运行状态。

Android 文档提供者不保证任意目标支持文件系统原子 rename，因此应用只能保证成功结果是结构完整且摘要有效的 ZIP。恢复器永远不接受缺少最终清单或摘要不一致的文件。

设置页记录最近一次成功的三类备份时间和目标显示名。这只是本机提示，不代表外部文件仍存在；不能显示“已安全备份”之类无法验证的承诺。

## 六、恢复流程与冲突规则

恢复必须先完整读取清单、预检展开大小、校验全部路径和摘要，再显示预览。用户确认前不修改 Registry、设置或 happ 数据。

统一入口按 `backupType` 路由：

- `settings`：展示将覆盖的设置项，只应用白名单字段；不创建或修改 happ。
- `happ`：沿用现有“恢复为新实例”流程；在某个 happ 设置内执行“恢复数据”时，只替换该实例的记录和文件，保留其代码、来源和 instanceId。
- `full`：展示备份时间、Hermit 版本、ready/archived happ 数量、预计空间和排除项，确认后恢复设置及全部实例。

全量恢复的默认目标是新安装或当前无 happ 的 HermitApp。若当前设备已有实例，不能按名称或 `happId` 静默覆盖；首版统一把备份中的 ready happ 恢复为新实例，已有实例保持不变。archived 数据恢复为新的 archived 实例。重复名称允许存在，并在结果页显示。需要“合并到既有实例”时，用户应在对应 happ 设置中显式使用现有的数据恢复入口，首版全量恢复不增加复杂的批量冲突编辑器。

恢复采用全量预检、分项 staging、最终提交：

1. 在私有临时目录校验并物化全部待恢复内容；
2. 为每个 happ 使用现有 Installer、RecordsStore 和 FileStore 合同创建新实例及新 data generation；
3. 任一项失败时删除本次新建实例和 staging，不修改原有实例；
4. 所有 happ 成功后应用 Hermit 设置、登记通知计划并重建 Scheduler；
5. 全部提交后输出恢复的设置项和实例数量，并列出按合同未恢复的敏感/设备状态；任一实例失败则整体回滚并报告失败项。

恢复不沿用备份中的本机 `instanceId`、Web Profile、记录 revision、系统权限或 grants；Native 重新生成这些状态。这样避免跨设备身份冲突，并保持现有单 happ 恢复安全边界。

## 七、HermitUI 交互

设置 → 系统新增“备份与恢复”区域：

- “立即备份全部”主操作；
- “备份 Hermit 设置”；
- “备份单个 happ”，展开后列出名称、图标、来源和当前版本，每行一个下载图标按钮；
- “从备份恢复”；
- 最近一次成功备份时间和失败状态。

备份按钮打开确认页，准确列出包含项、排除项和未加密提示。大包导出显示进度、当前 happ 和已写字节；用户可以取消。恢复先显示预览再确认，不能选择文件后立即修改数据。恢复期间禁止重复启动备份、安装、删除或另一恢复事务。

原有 happ 管理面板中的“导出应用备份”和“从备份恢复”继续存在，并与系统页单 happ 操作调用同一实现，不能维护两套格式或恢复逻辑。

## 八、实现边界

重构 `BackupCoordinator` 为可写入/读取流的核心逻辑，Android URI 选择器只负责取得输入输出流。新增外层 `HermitBackupCoordinator` 负责编排设置、全部实例和通知计划；它不能直接读取或复制其他模块的 SQLite 文件。

Registry 增加只读快照/迁移所需的小型查询接口；RecordsStore、FileStore、NotificationRepository 分别提供逻辑 export/import。所有恢复写入必须继续经过各模块自己的校验与配额，不允许为“完整恢复”绕开路径、大小、Origin、身份和文件摘要规则。

数据库升级先建立当前正式版本到新 schema 的逐版本 migration，并为每一步保留测试夹具。移除 `onUpgrade()` 中的删表重建路径；迁移失败时原数据库保持不变，启动原生恢复页，允许逐 happ 导出或选择已有备份恢复。

本计划不实现自动备份、后台定时任务、云端目录、目录持续同步、备份加密、WebView Profile 迁移、版本历史备份或全量恢复到既有实例的自动合并。

## 九、实施顺序与验收

### 阶段 A：无损升级门禁

实现 Registry 和通知数据库的非破坏性 migration；用上一正式 APK 生成含多个 happ、多个 release、记录和附件的真实数据，再同签名覆盖安装新 APK。

门禁：覆盖安装后实例数量、active release、记录、附件和当前启动均保持；迁移失败不会清库。

### 阶段 B：统一备份格式

抽取流式单 happ exporter/importer，加入外层清单、设置白名单、通知计划逻辑格式和三类自动文件名，同时保留 schema 3 单 happ 导入。

门禁：三种备份均能由清单独立识别；坏摘要、重复路径、路径穿越、超限、未知 schema 和截断 ZIP 全部在写入前被拒绝。

### 阶段 C：UI 与事务恢复

完成系统页入口、happ 列表、进度、取消、预览、确认和结果页；全量恢复使用 staging 与失败回滚，单 happ 管理入口切换到统一实现。

门禁：取消导出/恢复不改变原数据；失败恢复不留下半实例；已有实例场景不会被静默覆盖。

### 阶段 D：真机迁移验收

在目标荣耀/华为设备和另一台 Android 设备上执行：创建多个本地/线上 happ，写入记录与附件，设置通知，导出全部备份；卸载 HermitApp，重新安装同签名 APK，选择该外部 ZIP 恢复。

完成标准：外部备份在卸载后仍可由系统文件选择器找到；全部 happ 可启动，记录和附件一致，逻辑文件 ID 有效，设置和通知计划按合同恢复；历史 release、登录态、权限和开发凭据没有被错误恢复。随后再次覆盖升级，确认无需备份介入也不会丢失数据。

只有阶段 A-D 全部通过，才能对外声明“覆盖升级保留数据；卸载或换机前手工备份后可以恢复 HermitApp 与 happ”。不能把 APK 构建成功、单次模拟器导入或外部文件仍存在等同于完整恢复验收。
